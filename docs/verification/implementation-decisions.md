# 实施决策记录

以下按实施顺序记录需求未细化处的决定及其代价，供维护时追溯。已确认的产品需求以设计文档为准。

1. 最初无法写入 Git 元数据时，先保留文件快照和审查记录。代价：暂时无法用提交追踪变更；随后获得写权限，已由第 6 项取代。
2. 指定模型的协作接口返回不可用，团队改用可正常工作的默认模型。代价：运行成本可能与原先分配不同，任务边界和独立审查保持不变。
3. 按用户要求并行开发互不依赖的群聊、分块存储和界面，明确每个成员负责的文件。代价：最后需要核对跨模块接口。
4. 统一 HTTP 与桌面原生服务契约；使用 TURN 作为 P2P 中继，并保留服务器下载。代价：需要中继的网络须配置 TURN，否则走服务器。
5. 默认分块 4 MiB，单文件上限 20,000,000,000 字节；上传发布完成才开始计算 30 天，发布前验证各块与完整文件。代价：发布需要等待校验，换取内容完整性与访问隔离。
6. Git 写权限恢复后继续使用当前项目的功能分支。代价：以后若要另建隔离目录，需要迁移该分支。
7. 客户端构建问题与服务端认证修正分开并行处理、分别审查。代价：集成时需要再次核对共享接口。
8. 已验证分块在整个文件完成前即可共享，下载允许服务器与其他员工同时供给。清理仅作用于应用缓存和可确认归属的临时文件。代价：调度与缓存管理更复杂；员工保存的文件不被自动删除。
9. P2P 身份采用服务器认证的设备会话、逐次签名授权及 WebRTC 加密通道。代价：被盗令牌在撤销前仍有冒用风险；令牌仅在原生内存中保存，分块服务需要在线复核权限。
10. 文件元数据与实际存储作为一个可运行功能联合审查。代价：单次审查范围较大，但后续 P2P 可建立在已验证的完整文件流程上。
11. P2P 修正期间，仅并行添加独立的管理员、密码和设备方法，暂不变更已有认证入口。代价：最终注册接口时仍需集成验证。
12. P2P 源码复审通过后推进管理员完整集成，将真实网络测试继续保留为交付检查。代价：可能出现跨服务测试调整；源码通过不被当作运行通过。
13. 可配置双因素认证按设计中的增强项处理，与私聊、群公告一起列入后续阶段。代价：首期只有密码、首次改密和可撤销设备会话，不包含双因素认证。
14. 审计分别记录各来源贡献与实际保存完成，缓存复用不记成服务器流量。代价：需要持久化来源记录，避免恢复下载后错误归因。
15. 服务器为同时开始的设备协调不同起始区段，替代会碰撞的设备 ID 取模；协调失败仍能从服务器下载。代价：增加有容量与期限限制的协调状态和接口。
16. 完成管理员跨群管理、公共池上下架与共享策略、附件原始版本、后台提示及完成审计。下架保留永久文件且仅管理员可见；管理员管理群组不自动加入聊天；本地与管理员限制共同生效。代价：增加管理入口和数据库迁移，保持下架与删除的区别。
17. 离线、退出登录后仍清理已知过期缓存和归属明确的临时文件；在线优先刷新服务器期限，永久及有效缓存不因短暂错误被删除。代价：离线期间若服务器刚将普通文件提升到公共池，本机可能先删除旧缓存，重新联网后可再次下载，服务器文件和员工另存文件保留。

各阶段的源码审查、回归与真实运行结果见同目录的验证记录。开发过程中的完整原始台账保留在项目本地的 `.superpowers/sdd/2026-11-09-lan-collaboration-p2p-plan/`。
